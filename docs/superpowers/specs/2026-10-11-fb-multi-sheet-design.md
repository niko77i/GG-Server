# FB 户管看板：多表 + 户类型（子项目 B）设计

> 2026-10-11。**子项目 A（FB 单表 · 表头映射）已交付**（14 笔，终审「可以合并」，待人工验收）。
> 本文是 **B**：把 FB 从「一张表」升级成「一组表」，并让 FB 账户有自己的分类。
> **前置风险**：A 尚未人工验收；B 把 A 当底座（复用它的列映射面板与解析器）。

## 一、问题

TT 早就是「**多张账户表 + 户类型**」：一个户管配多张 Google 工作表，每张对应一个户类型
（如「加白户」「企业户」）；账户有分类；同步按表读、按分类回写；界面上每行两个按表按钮；
账户页有分类筛选。

**FB 现在只有一张表**（账户管理分配），没有分类。户管一旦需要第二张表（比如「加白户表」与
「企业户表」分开），就只能塞在同一张表里 —— 而两张表的表头、列顺序、需要关心的列都可能不同。

> **FB 的「恒单表」不是靠结构保证的，是靠一个空串约定撑的**（见 §三第 2 条）。
> 所以这次改造的要害不是「加功能」，而是**把这个隐式约定换成显式结构**。

## 二、已确认的决策（用户 2026-10-11 逐条裁定）

| # | 决策 | 出处 |
|---|---|---|
| 1 | **要**：FB 账户也按户类型区分（对齐 TT） | 用户选「要：FB 账户也按户类型区分（对齐 TT）」 |
| 2 | **户类型 = 资产类型**：直接存**每行的「资产类型」单元格值**（同一张表内可混多个） | 用户答「直接存每行的单元格值」 |
| 3 | **回写路由另存**「读自哪张工作表」，与分类解耦 | 用户选「另存『读自哪张表』（推荐）」 |
| 4 | **加 `account_type` 列**，存资产类型**原串**（接受与字典 id 漂移的代价） | 用户选「加，存资产类型原串」 |
| 5 | 走**方案 1**：在 TT 那套里加「按平台取分组键」的抽象，两个平台共用一份实现 | 用户选「方案 1，去写 spec」 |

## 三、现状事实（2026-10-11 只读侦察，见 `.superpowers/sdd/fb-multi-sheet-recon.md`）

   一次性迁移回填成 `'加白户'`，`:240-243`）。同步时逐行注入 `_account_type`
   （`routes/huguan_dashboard_routes.py:291-296`），`_collect_updates` 产出它
   （`py/huguan_dashboard.py:1462-1463`），`apply_diff` 消费它（新建写默认值、更新只在非空时写）。
2. **FB 的「单表」是四处影子同一个空串约定**（**这是本设计要拆掉的东西**）：
   - `get_platform_tables("fb")` 返回 `name: ""`（`py/huguan_dashboard.py:695-700`）
   - `group_rows_by_sheet` 按空串分桶
   - `routes/huguan_sheet_targets.py` 的 `_resolve_account_table` 用 `""` 命中
   - `_FB_ROW_SQL`（`:2213`）**不选** `account_type`（`_TT_ROW_SQL` `:2201` 有）
   ⇒ **漏改一处就静默串表**。
3. **`cross_sheet_notes` 是颗哑弹**：`py/huguan_dashboard.py:2305-2308` 对**任意平台**都
   `SELECT ... account_type FROM {table}`，而 `fb_accounts` 没这一列 —— 今天只靠
   「FB 的按表入口被 400 挡住」（`routes/huguan_dashboard_routes.py:188` 一带）才没炸。
   ⇒ **加列必须与放开按表入口同一批**。
4. **SQL 级只有一刀之差**：`_FB_ROW_SQL` 缺 `a.account_type`。给 FB 补这一列是整条链路
   最小但最关键的一步。
5. **前端多表 UI 骨架已存在**：`frontend/src/components/HuguanDashboardCard.vue:47` 的
   `v-else` 分支 **tt 与 fb 共用**（A 那批做的），fb 只是**隐藏了四样**（户类型名输入、删除、
   按表两个按钮、新增入口）⇒ B 的前端主要是**放开隐藏**。
6. **FB 早已走表头映射解析**（A 那批）：`routes/huguan_dashboard_routes.py:267` 的

7. **`OWNER_CHANNEL_COL` 刻意不含 fb**：依据在
   `docs/superpowers/specs/2026-10-06-fb-huguan-dashboard-design.md:272-287`（§6.5）——
   FB 那列写的是「旧转新」整串，不是新归属名。**B 不改这个**。
8. **运行库现状**：`fb_accounts` **0 行**、`fb_asset_types` 0 行、`fb_channels` 0 行

## 四、技术方案

### 4.1 数据模型：`fb_accounts` 加两列

| 列 | 类型 | 语义 |
|---|---|---|
| `account_type` | `TEXT DEFAULT ''` | **该行「资产类型」单元格的原串**（分类 / 筛选用） |
| `source_sheet` | `TEXT DEFAULT ''` | **该行读自哪张工作表**（回写 / 撤回路由用） |

- 两列都要在**建表语句**与**迁移区**两处都加（本仓库既有约定：`_add_column_if_missing`
  那里加过的列，建表语句里也要有，否则新建库缺列）。
- **不回填**（存量 0 行；且写死一个默认类型反而是错的）。
- ⚠️ **与放开按表入口同一批**（§三第 3 条的哑弹）。这是硬约束，实现顺序必须是
  「先加列 → 再放开入口」。

### 4.2 分组键抽象（方案 1 的核心）

现在「按户类型把行分组→落到各自工作表」这件事在几处各自实现，且都假设键是 TT 的 `account_type`。
本次抽出**一处**：「该平台的**分表键**」：

```
tt  → account_type   （值 = 表配置里的户类型名）
fb  → source_sheet   （值 = 工作表名）
gg  → 不参与（gg 恒单表，行为逐字节不变）
```

涉及的位置（**逐处清点，别漏**）：

| 位置 | 现在 | 改成 |
|---|---|---|
| `_TT_ROW_SQL` / `_FB_ROW_SQL` | fb 的缺 `account_type` | fb 的补 `account_type` 与 `source_sheet` 两列 |
| `collect_rows_for_push` | 按 `col_maps_by_type` 分桶 | 分桶键按平台取（tt: 户类型名 / fb: 工作表名） |
| `group_rows_by_sheet` | tt 按 `account_type`；fb 分空串桶 | 按平台取键；fb 用 `source_sheet` |
| `_resolve_account_table`（`huguan_sheet_targets.py`） | tt 按 `account_type` 查配置；fb 命中 `""` | 按平台取键：tt 从 `tt_accounts.account_type` 读、fb 从 `fb_accounts.source_sheet` 读 |
| `_owner_sheet_from` / 撤回按表 | 按 `account_type` | 按平台取键 |

> **为什么不让 fb 也按「户类型名」路由**：用户裁定同一张表里可以混多个资产类型（决策 2）
> ⇒ 「户类型」不再是「读自哪张表」的同义词，两者必须分开。

### 4.3 配置形态与迁移

FB 的配置从

```json
{ "spreadsheet_id": "...", "sheet_name": "账户管理分配", "columns": {...} }
```

改成（与 tt 同形）

```json
{ "spreadsheet_id": "...",
  "tables": [ { "name": "加白户", "sheet_name": "加白户表", "columns": {...} },
              { "name": "企业户", "sheet_name": "企业户表", "columns": {...} } ] }
```

- **读路径兜底，不批量改写磁盘**（照 TT 的 legacy 路径）：老配置只有扁平
  `sheet_name` ⇒ 当成**一条** `tables`，`name` 取该工作表名（`账户管理分配`）。
  写回发生在用户下次点保存时。
- `get_platform_tables("fb")` 改成与 tt 同形（带 `name` / `columns`）；
  **`save_config` 的「只允许 tt 写 tables」那条限制放开到 fb**。
- POST 校验：fb 从「顶层 `columns`」改成「`tables[].columns`」（与 tt 同规则、同白名单口径）；
  **`gg` 的载荷形状继续不变**（不含 `columns`、不含 `tables`、不含 `*_field_catalog`）。
- 配置 GET：fb 从「顶层 `columns` + `fb_field_catalog`」改成「`tables` + `fb_field_catalog`」
  （`fb_field_catalog` 保留，前端列映射下拉还要它）。

### 4.4 读路径（导入）

逐表循环（照 TT，A 那批已让 fb 走这段分支）：

- 每张表按**该表的表头**解析 col_map（已有）+ **该表自己的 `columns` 覆盖**（配置迁移后每表一份）。
- 每行注入两个合成键：
  - `_account_type` = **该行「资产类型」单元格的值**（**不是**表名、**不是**配置里的名字）
  - `_source_sheet` = **这张表的工作表名**
- 两个键都**无条件产出**（值缺失时为空串），理由同 TT 的 `_account_type`：
  缺键会让已存账户被判成「变了」⇒ 整行虚报「将更新」。
- 定位键（资产UID）认不出 ⇒ **拒绝本次同步**（A 已有，逐表生效）。
- 未采集列**逐表**上报（A 已有）。

### 4.5 写路径（刷新回表）

- **按 `source_sheet` 选表**（不是按户类型）。
- `source_sheet` 为空或指向一张**已不在配置里**的表 ⇒ **跳过该账户并记 warning**，
  **绝不退回写第一张表**（那会把甲表的内容覆盖进乙表）。
- 按表刷新（给了 `sheet_name`）时，只处理该表：`source_sheet` 等于它的账户。
- 归属变更 / 备注 / 接户运营的定向回写**沿用 A 的 col_map 定位**（B 不动）。

### 4.6 撤回

- 快照按 `source_sheet` 分表；按表操作的快照**只含那一张表**（照 TT，否则撤回范围会扩散）。
- 撤回时逐表回退，定位键与列字母取**该表的 col_map**（A 已有）。
- `sheet_back_sheets`（`{account_id: sheet_name}`）的构建键改成 `source_sheet`。

### 4.7 按表入口

- **后端**：`/sync` 与 `/push` 各加可选 `sheet_name`，给了就只处理那一张
  （TT 已有这套，B 是把 `platform != "tt"` 的门控放开到 fb）。
- **前端**：把 A 那批对 fb **隐藏的四样**放开——户类型名输入、删除按钮、按表两个按钮、
  「＋ 新增户类型」入口；平台级两个按钮改文案「全部导入 / 全部刷新」并挂列出所有表的 tooltip。
- 跨表重复提示（`cross_sheet_notes`）：按表操作时**只查库、不读别的表**（照 TT，避免抵消提速）；
  放开 fb 之前**必须先加列**（§4.1 的硬约束）。

### 4.8 账户页

- FB 账户页加「**户类型**」筛选按钮，选项 = **当前该户管账户里实际出现过的 `account_type` 去重**
  （**不是**字典全量——资产类型字典里可能有他一个账户都没有的类型）。
- 后端 `fb_routes` 的列表查询加 `account_type` 筛选参数；筛选与分页叠加（该页已是服务端分页）。
- 账户表加一列「户类型」显示。

### 4.9 两份真相的口径（`asset_type_id` vs `account_type`）

用户已接受漂移的代价，但**必须定一个口径**，否则以后没人知道该信哪个：

- **`asset_type_id`**（字典 id）——只管**表里「资产类型」那一列的读写**（既有行为不变）。
- **`account_type`**（原串）——**界面上的分类与筛选一律以它为准**。
- **同步时 `account_type` 一律用表里那个单元格刷新**（含清空：表里清空 ⇒ 账户的分类也清空）。
  ⇒ 字典改名造成的漂移，**最迟下次同步自愈**。
- 更新已存账户时，`account_type` / `source_sheet` **只在非空时写**（照 TT 对 `account_type`
  的既有口径：空值不覆盖，避免「表里那格空着」把已有分类擦掉）。

⚠️ **但只做「非空才写」还不够，会踩 TT 踩过的那个坑**：两个键在 §4.4 里是**无条件产出**的
（值缺失时为空串），而 `_same_as_existing` 会拿它跟库里的值比 —— 若库里是「企业户」、
本次产出是空串，**每一行都会被判成「变了」⇒ 整份报告虚报「将更新」**。
TT 没这问题，是因为它的 `_account_type` 恒为**非空**的表类型名。

⇒ **判据要一起改**：`_account_type` / `_source_sheet` 这两个键在 `_same_as_existing` 里
**「本次产出为空」一律视为「无变化」**（空 = 表里那格空着 = 不覆盖）。
这一条要有专门用例：**库里分类非空 + 表里那格空着 ⇒ 该行不进 `to_update`**。

## 五、非目标

- **GG 一个字不动**（它恒单表，且不在本次范围）。
- **TT 的行为不变**：本次只在它那套里加「按平台取分组键」的抽象，TT 的键仍是 `account_type`。
- **不动 `OWNER_CHANNEL_COL`**（FB 那条「旧转新」通道的语义是 §三第 7 条的裁定）。
- 不做「户类型的重命名级联」（TT 有：改类型名会级联改账户的 `account_type`）。
  B 不做——因为 **FB 的户类型是数据驱动的**（来自单元格），改名应该改表、不是改配置。
  ⚠️ 这一条要在验收时显式确认：**改配置里的「户类型名」不会动账户的分类**（那是对的）。
- 不做 FB 的字典项自动补建扩展（A 之前那批已覆盖渠道/资产类型）。

## 六、风险与缓解

| # | 风险 | 缓解 |

| 1 | **哑弹**：`cross_sheet_notes` 对 `fb_accounts.account_type` 的 `SELECT` 会炸 | **加列与放开按表入口同一批，顺序固定**（加列在前）；加一条「放开入口后调 cross_sheet_notes 不报错」的用例 |

## 十、未决项

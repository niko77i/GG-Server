# 户管看板同步撤回（子项目 ③）设计

> 日期：2026-10-06
> 范围：给户管看板的两个手动同步按钮加「撤回上一次」。
> 前置：子项目 ①（FB 资产数据模型）与 ②（FB 户管看板）均已交付并门禁全绿。
> 覆盖平台：**gg / tt / fb 三个**。

---

## 一、需求描述

用户 2026-10-06 原话：

> 「我希望同步的时候，可以撤回上一次的同步，不管是系统到表还是表到系统，就像Google的表有历史记录一样」

---

## 二、已定决策汇总（用户 2026-10-06 逐条确认）

| # | 决策点 | 结论 |
|---|---|---|
| 1 | 撤回语义 | **分方向**：系统→表用**整片快照**写回；表→系统用**增量回滚** |
| 2 | 表→系统撤回时的新建对象 | **没被动过的才删**，动过的保留并列为冲突 |
| 3 | 快照粒度 | 每个 (户管 × 平台 × 方向) **只留最近一条** |
| 4 | 覆盖范围 | **只覆盖两个手动按钮**，不覆盖自动回写 |
| 5 | redo / 多步历史 | **都不做** |

### 决策 1 的理由

- **系统→表**：那张表是**户管一个人的**，整片写回的最大代价是他自己在表里的手改被退回 —— 覆盖风险低，实现简单，语义也最贴合「像 Google 的历史记录」。
- **表→系统**：库是**多人共用的**。整片「时光倒流」会静默抹掉同步之后所有人对这些账户的改动。所以只反向撤销**本次同步实际改过的那几列**。

### 决策 4 的理由

自动回写是「户管在面板上编辑某个账户」的**副作用**。单独撤掉它，只会让表停在旧值、而库里已是新值 —— 表和系统当场不一致。要撤那次编辑，撤的应该是「编辑账户」这个动作本身，那是另一个功能（目前不存在）。

## 三、关键事实（已核实，决定了方案形状）

### 3.1 Google 那边借不到力

Sheets / Drive API **没有「恢复到历史版本」的接口**。Docs / Sheets 类型的 revision 不能删也不能回填；官方唯一的 workaround 是导出旧版本再**整文件覆盖**，那会把整个表格（含户管在里面的其它工作表）一起冲掉。

⇒ **必须自己存快照。** Google 只提供人肉恢复的 UI，不提供可编程的撤回。

### 3.2 仓库已有形状先例，但不能直接用

`audit_log` 表 + `POST /api/audit-log/restore/<log_id>`（`py/main.py:3517`，仅 developer）：
删除产品前把完整 JSON 快照塞进 `detail`，恢复时按快照重建。

**可以借形状，不能共用这张表**：它只管 `delete_product` 一个动作，粒度是「一个被删对象」，而本需求是「一次同步会话里的 N 处改动」；且它的列表端点带 `@no_huguan`，明确拒绝户管。

### 3.3 三个平台的表侧写点现在不一样（② 期间的变化）

原设计写这份文档时只有 GG/TT，且两者都用「变更通道列」。现状已不同：

| 平台 | 归属列 | 记录/通道列 | 撤回时要回退的「表侧」内容 |
|---|---|---|---|
| GG | G 运营 | H 重新分配（`_owner_channel`，通道协议） | 运营列改写 + 通道列清空 |
| TT | G 接户运营 | L 换绑情况（`owner_change_note`，**只读回不回写**） | 运营列改写（**无通道列可清**） |
| FB | J 在用运营 | I 接户运营（`acceptor`，定向写） | 在用运营列改写 + 接户运营列的 `{旧}转{新}` 记录 |

⇒ 撤回的「表侧回退」逻辑**必须按平台分流**，不能照 GG 写死。

## 四、数据结构

### 4.1 新表 `huguan_sync_undo`

```sql
CREATE TABLE IF NOT EXISTS huguan_sync_undo (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id     INTEGER NOT NULL REFERENCES users(id),
    platform    TEXT    NOT NULL,
    direction   TEXT    NOT NULL,          -- 'push' | 'sync'
    created_at  TEXT    DEFAULT (datetime('now','localtime')),
    payload     TEXT    NOT NULL DEFAULT '{}',
    UNIQUE(user_id, platform, direction)
);
```

- `UNIQUE` 约束实现「每个户管每个平台每个方向只留最近一条」—— 写入用 `INSERT OR REPLACE`，**不需要清理策略**
- `direction='push'` 指「刷新到看板」；`'sync'` 指「从表同步到系统」
- payload 存 JSON

### 4.2 为什么不复用 `audit_log`

见 §3.2。两个功能的生命周期不同：审计是**只增不减的历史**，撤回快照是**用完即弃的一次性凭据**。混用会让「谁被删了」和「刚刚能撤回什么」两个概念纠缠。

## 五、记录时机

### 5.1 `push` 方向（系统 → 表）

在 `dashboard_push` **写表之前**：

1. 整片读一次表（`READ_RANGE[platform]`）
2. 按定位键（GG/TT 的 C 列 / **FB 的 D 列**）建索引，算出 `rows` 里**真正会被写**的那些账户
   （表里没有的账户本来就不写，不进快照）
3. 记下这些行**将被写的每一个格子**的当前值
4. 写快照 → 写表 → **成功保留、失败删除**（没写成，无可撤回）

payload 形状：

```json
{
  "spreadsheet_id": "...", "sheet_name": "...",
  "cells": [{"account_id": "...", "cells": {"D": "旧值", "G": "旧值"}}]
}
```

### 5.2 `sync` 方向（表 → 系统）

在 `apply_diff` **执行之前**收集、**执行之中**补全：

| 字段 | 内容 |
|---|---|
| `updates` | 按账户ID 记 `{列名: 旧值}`（只记本次真正会改的列） |
| `owner_changes` | 按账户ID 记旧的 `owner_id` 与旧归属名 |
| `created` | 本次新建的账户ID 列表（**不存行主键**，撤回时按账户ID 反查） |
| `created_statuses` | 本次新建的状态 `{name, platform}` |
| `sheet_back` | 落库后回写表的那几列的**原值**（按平台，见 §3.3） |

**不存历史行 id**：撤回改回 MCC / BC / 主 BM 时复用既有的 `_record_channel_change` /
`_record_bm_change`，会**自动补一条历史** —— 这符合仓库既有契约（任何 MCC / BC 变更都要留痕），
撤回也不该是绕过留痕的后门。新建账户被删时，历史行由 `ON DELETE CASCADE` 一并清掉
（`account_mcc_history` / `tt_account_bc_history` 有；**`fb_account_bm_history` 没有，见 §9**）。

快照以**业务键**（账户ID、状态名、BM 名）为主，不存行主键 —— 反查即可，更抗数据变化。

### 5.3 快照的生命周期（两个方向同一条铁律）

**快照只在「该次写入完整成功」之后才有资格被撤回。** 具体地：

- `push`：写表成功 → 保留；写表失败或抛异常 → **删除快照**（表没变，撤回没有意义）
- `sync`：`apply_diff` 正常返回 → 保留；`apply_diff` 抛异常（中途失败）→ **删除快照**
  （部分落库的库状态无法用一份残缺快照安全反向）
- 撤回本身：**两边都成功之后**才删快照（见 §6.2）

### 5.4 删用户时要清理本表

`huguan_sync_undo.user_id REFERENCES users(id)` 且**无 `ON DELETE`**，而连接开着
`PRAGMA foreign_keys=ON`（`database.py:42`）。`admin_delete_user` 必须把该用户的
`huguan_sync_undo` 行一并删除，否则删任何用过看板的户管都会以
`FOREIGN KEY constraint failed` 收场。

这属于仓库既有的「删用户时的关联清理」清单（见 `AGENTS.md` 的那条口径），
**加一张表就必须同时加进那个清单**。

## 六、撤回执行

### 6.1 `push` 撤回（系统 → 表）

- 把快照里的格子走现成的 `update_rows_by_account_id` 写回
- **无条件写回**，不做 CAS：push 的语义是「整表对齐到系统」，撤回就是退回对齐之前。
  中间发生的自动回写会在下次 push 时重新对齐
- 表里已找不到的行 → 计入 `not_found` 报告，不报错
- 表写完后删除快照

### 6.2 `sync` 撤回（表 → 系统）

> **顺序必须是：先回退表，再回退库。不能反。**

反过来的后果是实的：先回库再回表，一旦表那步失败 —— 库里 `owner` 已回到张三，
而表里运营列还是李四、通道列已清空 —— 下次同步会判定「运营列李四 ≠ 库里张三」产生归属变更，
**把撤回又自动撤销掉**。顺序对了，最坏只是表回退了、库没回退，下次同步不会误改。

**库部分（单事务）**：

- 逐 `updates` / `owner_changes`：**compare-and-swap** —— 当前值 == 本次写入的新值才写回旧值；
  不等则**跳过并列为冲突**，绝不覆盖别人后来的改动
- 删 `created` 里的账户：`updated_at` 仍等于建号时的值 → 删；变了 → 保留并报冲突
- 删 `created_statuses`：`account_statuses` 里无人引用 → 删；有引用 → 保留并报冲突
- `commit`

**表部分**：把 `sheet_back` 的格子按平台分流写回（GG 的运营+通道、TT 的运营、
FB 的在用运营+接户运营）。这几列都是系统自己写的，无条件退回。

**快照保留到库提交成功之后才删** —— 中途失败可以重试；表写入是**幂等**的（写固定值，不是增量）。

## 九、三条必须带进来的约束（② 期间攒下的）

1. **`fb_account_bm_history` 没有 `ON DELETE CASCADE`**（`account_mcc_history` /
   `tt_account_bc_history` 都有）。sync 撤回删新建 FB 账户时，**必须显式先删该表的历史行**，
   否则 `PRAGMA foreign_keys=ON` 会以外键挡下删除。
2. **`fb_accounts.acceptor` 是 TEXT**（复合串 `"{旧}转{新}"`），撤回时按普通文本列处理，不做名称解析。
3. **FB 没有变更通道列**。GG 的撤回要「清空通道列」，TT 和 FB **没有这一步**（TT 的
   `owner_change_note` 只读回不回写；FB 的 `acceptor` 靠定向写维护）。按 §3.3 的表格分流。

## 十、回归保障

新增 `py/tests/test_huguan_undo.py`：

1. **快照记录**：push 写表前记原值；表写下失败则不留快照
2. **push 撤回**：格子恢复原值；表里已删的行进 `not_found`
3. **sync 撤回的 CAS**：当前值 == 新值 → 写回旧值；被改过 → 跳过并报冲突（两种各一条）
4. **新建对象**：未动过的账户被删（含其历史行随 CASCADE 一并消失）；动过的保留并报冲突；
   无引用的状态被删、有引用的保留
5. **顺序约束**：库那步失败时表已回退，且**不会**导致下次同步自动重做归属变更
6. **只撤自己的**：另一户管的记录取不到
7. **三平台分流**：GG 撤回会清通道列；**TT 与 FB 不会**（各自只有运营/在用运营那一列）
8. **FB 特有**：删新建 FB 账户时 `fb_account_bm_history` 被显式清理，不撞外键
9. **快照不被自动回写覆盖**：`writeback_rows` 不写入 `huguan_sync_undo`

`cd frontend && npm run build`。

## 十一、风险与已知代价

1. **`sync` 撤回只能撤销「没被别人动过」的部分。** 这是 CAS 的必然结果，也是安全的来源 ——
   宁可少撤、报冲突，也不覆盖别人后来的改动。
2. **快照只留最近一条。** 连续两次同步后，第一次的就撤不回来了。这是决策 3 的直接结果。
3. **`push` 撤回会无视中间的自动回写**，把表退回刷新前。这是「无条件写回」的代价；
   语义上正确（push 本来就是整表对齐），但要在确认文案里说清。
4. **撤回本身不是原子的**：表与库是两处副作用。实现上靠「先表后库 + 快照保留到库成功」把
   失败窗口收窄到可重试，但**不是**数据库意义上的原子操作。
5. **删除新建账户会连带删除它这段时间获得的一切**（挂的 MCC/BC/BM、变更历史、别人的编辑）。
   决策 2 的 `updated_at` 判定只保护「同步之后被编辑过」的账户；纯挂接类的改动不更新
   `updated_at`，可能检测不到。
6. **`sync` 撤回的字段类回退不跨下一次同步持久。** `sheet_back` 只覆盖归属/运营相关的表侧列
   （§3.3），字段类更新（如 `unit_price`、数量、日期等）只在**库里**回退、**表里不回退** ——
   下一次「从表同步到系统」会重新把表里的新值 diff 出来再落库。因此撤回字段类更新
   只在「表未被再次同步」的窗口内有效。

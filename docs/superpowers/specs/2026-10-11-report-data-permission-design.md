# 数据管理页开放给管理员/户管（户管可改消耗、管理员只读）设计

日期：2026-10-11
状态：待确认
前置：用户原话与逐轮澄清见 §8「已定案」

---

## 1. 需求

### 1.1 用户原话

> 现在这个数据管理的页面，GG FB 都是有的，但是只对向个人，现在需要开发到管理员和户管。并且户管有编辑消耗的权力，管理员只有看的权力。

### 1.2 澄清后的目标

- **范围**：GG 数据管理页（`/data-manage`）与 FB 数据管理页（`/fb/data-manage`）两张。**TT 不涉及**（TT 没有这个页面）。
- **可见范围**：跨用户角色（户管 / 管理员）看**全部用户**的数据。
- **户管**：**只能改「消耗」一个字段**；不能改其他字段、不能新增、不能删除、不能批量删除。
- **管理员**：**只读**（不能改任何字段、不能增删；可以导出 CSV；不能重试写表）。
- **普通 user**：**仍然只看自己的数据**，权限逐字不变。
- **「消耗」的编辑形态**：**列表内联编辑**（点 ✏️ → 输入框 → 回车/失焦保存）。
- **新增**：加一个「**保存人**」筛选（跨用户角色可见），否则看全部时找不到某人的数据。

### 1.3 非目标

- 不做「按账户归属（`owner_id`）收窄」——见 §2.3 的隔离轴说明，本期就是「跨用户角色看全部」。
- 不改 TT（无此页面）。
- 不改账户面板（`AdsAccountPanel` 等）的任何行为。
- 不引入「按角色预设默认筛选」这类额外机制。

## 2. 现状与根因（探索所得，附出处）

### 2.1 页面本体

| 平台 | 页面 | 入口 |
|---|---|---|
| GG | `frontend/src/views/DataManageView.vue` | `/data-manage`（`router/index.js:89-92`；侧边栏 `AppSidebar.vue:77`） |
| FB | `frontend/src/views/fb/FbDataManage.vue` | `/fb/data-manage`（`router/index.js:143-146`；侧边栏 `AppSidebar.vue:94`） |

- GG 页有：筛选（产品/日期/搜索/列显示）、**新增**、导出 CSV、批量删除、每行编辑/删除；「花费」列 `DataManageView.vue:149-161`，编辑弹窗内含花费输入 `:118`。
- FB 页有：筛选（产品/线名/日期）、导出 CSV、批量删除、查看统计、每行编辑/删除、写表失败汇总+重试；「消耗」列 `fb/FbDataManage.vue:53`，编辑弹窗内含消耗输入 `:78`。**FB 没有「新增」。**
- **户管的侧边栏里没有数据管理入口**（`AppSidebar.vue` 的 `huguanNavItems` / `huguanFbNavItems` 均不含）。
- **FB 对户管有显式路由拦截**：`router/index.js:236-239` 把 `/fb/data-manage` 重定向到 `/fb/accounts`。GG 无对应拦截（户管手输能进，但后端只回自己 uid 的空数据）。

### 2.2 接口现状（作用域）

**GG `/api/ad-reports/*`（`py/main.py`）—— 读写**全部**按 `user_id = 当前 uid`，零跨用户：**

- `list` `main.py:10050`：`where = ["user_id=?"]; params=[user_id]`
- `export` `:10188`（复用同一 where 构造）
- `PUT <id>` `:10227`：`SELECT id FROM ad_reports WHERE id=? AND user_id=?`（仅 owner）
- `DELETE` `:10274`、`batch-delete` `:10293`：同样带 `AND user_id=?`
- `save`（新增）`:9810` 起的路由

**FB `/api/fb/reports/*`（`py/routes/fb_routes.py`）—— 读窄写宽（现存不一致）：**

- 读仍只看自己：`list` `:2201`、`stats` `:2330`、`export` `:2478`、分析 `_fb_analysis_where` `:2367`
- 写已放宽到 `CROSS_USER_ROLES`：`update` `:2236`、`delete` `:2263`、`batch-delete` `:2309`
- **⇒ 户管/管理员现在能改、删自己根本看不见的行**（读接口不返回它们）。

### 2.3 关键约束：隔离轴是 `user_id`，不是 `owner_id`

- `ad_reports`（`py/database.py:584`）与 `fb_ad_reports`（`:924`）**都没有 `owner_id` 列**，归属轴是 **`user_id` = 谁保存的这条**。
- 这与账户类资源（`accounts.owner_id`）**不是一回事**。所以本设计里的「跨用户」= 去掉 `user_id` 限定，而**不能**照搬账户面板那套「按 `owner_id` 收窄」。这也是 §1.3「不做按归属收窄」的原因：技术上要先把行里的账户号关联到账户表才能算出归属，GG 存的是账户名/客户ID、FB 存 `account_id`，两边路径还不一样，不是本次该做的事。

### 2.4 可复用的范式

- 账户面板的「跨用户三态」：`main.py:4027` `_cross_user_actor(user_id)` → `:4088-4110` 的
  `非跨用户 → WHERE owner_id=?` / `跨用户 → 不限定（可选按 owner_id 收窄）`。
- `py/routes/helpers.py:5` `CROSS_USER_ROLES = ("developer", "admin", "huguan")`；
  同文件 `:137` `scope_where`、`:148` `can_modify` 是既有的「共用权限件」先例。
- FB 的写校验范式：`py/routes/fb_routes.py:2534` `_get_role(db, uid)` + `not in CROSS_USER_ROLES` 判断。

## 4. 技术方案

### 4.1 后端：判定抽到 `py/routes/helpers.py`，两个平台共用（方案 B）

新增两个函数（该文件已有同类先例）：

```python
def report_scope_where(role, uid, filters) -> tuple[str, list]:
    """报表类资源（ad_reports / fb_ad_reports）的可见作用域。

    与账户类不同：这两张表**没有 owner_id**，归属轴是 user_id（谁保存的）。

    - 非跨用户角色 → ["user_id = ?"] + [uid]（**与现行为逐字等价**）
    - 跨用户角色（developer/admin/huguan）→ 不加 user_id 限定（看全部）；
      若 filters 带 user_id（前端「保存人」筛选）则追加 "user_id = ?"
    调用方再把产品/日期等各自的条件追加进去。
    """

def report_editable_fields(role) -> set[str]:
    """该角色在数据管理页可改的字段集合。**空集 = 只读**。

    - developer → None（表示"全部字段"，调用方不设白名单）
    - huguan    → {"cost"}
    - 其余（含 admin）→ set()   ← 管理员只读
    """
```

### 4.2 接入（两个平台同构）

| 端点 | 改动 |
|---|---|
| `list` / `export` / `stats` | WHERE 改走 `report_scope_where` ⇒ 跨用户角色看到全部；普通 user 不变 |
| `PUT <id>` | 归属校验放宽到 `CROSS_USER_ROLES`；**再叠字段白名单**：请求体里出现白名单外的字段 → **403**（不是静默忽略）。户管只能传 `cost`；admin 传任何字段都 403 |
| `DELETE <id>` / `batch-delete` | `role in ("admin","huguan")` → **403**（developer 仍可） |
| `save`（GG 的新增） | 同上 → 403 |
| FB `retry-sync` | `role == "admin"` → **403**（户管/developer 可） |

**顺带修掉 §2.2 那处不一致**：FB 的读写都改走同一份判定后，「能改看不见的行」这件事自然消失。

### 4.3 前端：按角色控制入口

| 改动 | 文件 |
|---|---|
| 户管侧边栏加数据管理入口 | `AppSidebar.vue` 的 `huguanNavItems` / `huguanFbNavItems` |
| 去掉 FB 对户管的路由拦截；核对 GG 放行 | `router/index.js:236-239` |
| 按角色隐藏「新增 / 删除 / 批量删除」 | `DataManageView.vue`、`fb/FbDataManage.vue` |
| 「消耗」列内联编辑（仅户管） | 同上；照 `AdsAccountPanel.vue` 的内联编辑范式（点 ✏️ → 输入框 → 回车/失焦保存，**只提交 `cost` 一个字段**） |
| 「保存人」筛选（仅跨用户角色） | 同上；下拉数据源用现成的用户列表接口，选中后传 `user_id` 给 list |
| auth store 加 getter | `stores/auth.js`（如 `canEditReportCost`、`canManageReports`、`canFilterReportOwner`） |

> **本节含新增 UI**（内联编辑入口 + 按角色显隐），按项目规范实现前**必须先调 `/frontend-design`**。

## 5. 影响面与风险

### 5.1 这是一次**权限收紧**，会改变现有真实账号的行为

真实库（只读统计）里，**FB 平台**的 `admin` 有 **1 人**、`user` 有 5 人；GG 平台的 `admin` 6 人、`user` 1 人。

- **管理员**：现在对 FB 报告有改/删/批删权（`fb_routes.py:2236/2263/2309` 已放宽），改后**全部变只读**。受影响的实际是 **FB 那 1 个 admin**（GG 侧 admin 本来就没有写权 —— GG 的写接口一直只认 owner）。
- **户管**：现在有 FB 的增删改权，改后**只剩「改消耗」**。

（`admin`(tt) 虽有 3 人，但**本次不触及 TT** —— 改的两个端点是 `/api/ad-reports/*` 与 `/api/fb/reports/*`，TT 管理员不经过它们。）

这是需求要的效果，但**上线后这些人会立刻感受到权限变小**，需知悉。

### 5.2 其它风险

| 风险 | 处置 |
|---|---|
| 看得见的数据量骤增（全部用户的行） | 靠分页 + 新增的「保存人」筛选；若仍嫌大，后续再议（本设计不加服务端 LIMIT，沿用现状） |
| 前端隐藏了按钮但后端没拦 | 后端是唯一权威（每个写端点都判角色）；前端隐藏只为不误导 |
| 两套角色判定漂移 | 本方案的全部意义所在：**只此一份**（§4.1） |
| 普通 user 行为被改坏 | §3 把它列为回归硬判据，逐字不变 |

## 6. 边界与错误处理

| 场景 | 行为 |
|---|---|
| 户管提交了 `cost` 以外的字段 | **403**，错误文案说明「仅可修改消耗」 |
| 管理员调任何写端点 | **403** |
| 户管/管理员删行、批量删、新增 | **403** |
| 普通 user 传别人的行 id 去改 | 403（`user_id` 不匹配，**现行为不变**） |
| 未登录 | 401（沿用 `@jwt_required`） |
| viewer 访问该页 | **本次不动，且行为不变**。⚠️ 自审时纠正了一处误判：viewer 的守卫规则（`router/index.js:214-218`）**只在 `/accounts*` 路径内生效**（把 viewer 从其他账户子页弹到 `/accounts/products`），**并不拦 `/data-manage`** —— 所以 viewer **能打开**该页，看到的是**自己的行**（通常是空的）。viewer 不在 `CROSS_USER_ROLES` 里 ⇒ `report_scope_where` 给他们的是 `user_id = ?` ⇒ **跨用户开放与他们无关**。这是**现状**，本次不改。（附带观察，**不在本次范围**：viewer 因此对自己名下的行仍有写权，而该角色语义是只读 —— 是否收紧另议。） |
| 「保存人」筛选传了非法 user_id | 按形状校验回 400（沿用同仓口径）；非跨用户角色即使传了 `user_id` 也只返回自己的行（**不得因该参数越权**） |

## 7. 测试与验收

**后端**（`py/tests/`，新增 `test_report_data_permission.py`）：
- **普通 user 回归**：list/export/update/delete 的作用域与改动前**逐字一致**（自己行可见可改，别人行不可见不可改）
- **户管**：list 返回全部用户的行；`PUT` 传 `cost` → 200；传 `cost` + 任意其他字段 → **403**；`DELETE`/`batch-delete`/`save` → 403；`export` → 200
- **管理员**：list 返回全部；`PUT`/`DELETE`/`batch-delete`/`save`/`retry-sync` 一律 **403**；`export` → 200
- **developer**：全权（回归）
- **「保存人」筛选**：跨用户角色传 `user_id` → 只返回该人的行；**普通 user 传别人的 `user_id` → 仍只返回自己的行**（不得越权）
- GG 与 FB **两侧都要**（端点不同，一份判定两个调用点）

**前端**（无测试基建，走真实运行）：
- 三种角色各进一次两张页面：按钮显隐、内联编辑入口、「保存人」筛选是否出现
- 户管改一行消耗 → 落库；刷新后仍在
- 普通 user 的页面与改动前**完全一致**

**验收判据（用户视角）**：
> 户管进数据管理页，看到所有人的数据、能直接改某一行的消耗、看不到新增/删除；管理员进同一页，全都看得到但一个都改不了。

## 8. 已定案

| # | 问题 | 决定 |
|---|---|---|
| 1 | 跨用户看谁的数据 | **全部用户** |
| 2 | 户管的编辑权到哪儿 | **只改「消耗」一个字段**（不能改其他字段、不能增删） |
| 3 | 导出 / 重试写表怎么算 | **两者都给户管；管理员只能导出**（不能重试） |
| 4 | 「消耗」的编辑形态 | **列表内联编辑** |
| 5 | 实现方案 | **B：抽到 `helpers.py`，两个平台共用** |
| 6 | 「保存人」筛选 | **要** |
| 7 | 普通用户 | **仍只看自己的数据**（权限逐字不变） |

### 尚待你确认的一处（我按推荐先写进设计）

**户管提交白名单外的字段时回 403，而不是静默忽略。** 理由：静默忽略会让前端以为「改了但没生效」，而后端拒绝会明确告诉调用方越界了；且 403 让越权尝试在日志里可见。

**若你更想要「静默只取 cost、其余丢弃」，说一声，改一行。**

## 附录：数据管理页视觉决策

> 2026-10-11 按项目规范，动组件前经 `/frontend-design` 产出。**本附录为纯新增，前文结论章节一字未动。**

### A.1 设计输入（约束先于创意）

1. **沿用两页既有的 Element Plus 形态**，不另起一套视觉 —— GG 页与 FB 页风格本就相近。
2. 「消耗」列**内联编辑**：照 `views/AdsAccountPanel.vue:53-60 / 702-744` 的既有范式（点 ✏️ → 输入框 → 回车/失焦保存），只对**户管**出现。
3. **按角色显隐**：非 owner 角色不渲染「新增 / 删除 / 批量删除」；**管理员连内联编辑的 ✏️ 都不出现**。
4. **「保存人」筛选**：仅跨用户角色可见的下拉，放在现有筛选栏里，文案与既有的「产品 / 日期」一致。
5. 只读角色（管理员）的界面要让人**一眼看出是只读**，而不是点了才被拒。

结论：这**不是**一次视觉再设计，而是一次**角色可见性**设计。因此「大胆只花在一处」——唯一的新视觉元素是角色标识 chip，其余全部复用既有语汇。

### A.2 令牌（全部取自本仓既有值，零新增色）

| 用途 | 值 | 出处（本仓既有） |
|---|---|---|
| 能力色（可编辑） | `#0891b2` | 侧边栏激活态 / `detail-item.active` / `plat-btn.active` |
| 能力色淡底 | `rgba(8,145,178,0.10)` | 同上（既有用 0.08–0.12） |
| 中性灰（只读） | `#6b7280` / 底 `#f3f4f6` / 边 `#e5e7eb` | `DataManageView.vue` 的 `.page-desc` / 侧边栏边框 |
| 数字对齐 | 右对齐（沿用列的 `align="right"`） | 两页既有 `cost` 列定义 |

字体：不引入新字族，沿用 Element Plus 默认（新增元素里只有 12px 的 chip 与既有 13px 的正文层级）。

### A.3 布局

```
改前（普通 user，逐字不变）：
  📋 数据管理
  [产品▾] [日期 ~] [搜索] [列显示]        [刷新][导出CSV][➕新增][🗑批量删除]
  ☑ | 产品 | 日期 | … | 花费 | … | 操作(编辑/删除)

户管（可看全部 + 只可改消耗）：
  📋 数据管理  (可改「消耗」)
  [保存人▾][产品▾] [日期 ~] [搜索] [列显示]      [刷新][导出CSV]      ← 无新增/无批量删除
  | 产品 | 日期 | … | 花费 $12.50 ✏️ | …                              ← 无勾选框、无操作列

管理员（只读）：
  📋 数据管理  (只读)
  [保存人▾][产品▾] [日期 ~] [搜索] [列显示]      [刷新][导出CSV]
  | 产品 | 日期 | … | 花费 $12.50 | …                                 ← ✏️ 也不出现
```

- 对齐：标题左对齐，chip 紧贴标题右侧（同一行），筛选栏左组 / 右组沿用既有分组。
- **保存人下拉放筛选栏最左**：跨用户角色下「看谁的数据」是首要问题，产品/日期是其次；它只对跨用户角色渲染，故普通 user 的筛选栏一个像素都不移动。
- **只读 = 做减法**：勾选框列与「操作」列整列不渲染（不是灰掉）。留着勾选框却无批量动作、留着「编辑」却必被 403，都是误导。

### A.4 逐项决策

| # | 决策 | 理由 |
|---|---|---|
| 1 | 标题右侧一枚 chip：管理员「只读」（中性灰）／户管「可改『消耗』」（薄荷青淡底） | 满足 brief 第 5 条「一眼看出只读」。用**状态**而非**警告**语气：只读是本需求刻意的授权结果，不是错误，所以不用琥珀/红 |
| 2 | 内联编辑**逐字复用** `AdsAccountPanel` 的 `.inline-edit-cell / .inline-cell-text / .inline-edit-btn`（✏️ 平时 `opacity:0`，悬停才现） | 同一套交互心智；`opacity` 而非 `display` ⇒ 出现时数字不跳位 |
| 3 | 内联编辑**只在户管分支里**包一层 `v-if`，其余角色走**原来的那一行渲染** | 保住「普通 user 与改动前逐字一致」这条硬判据（否则 flex 包裹会让右对齐失效） |
| 4 | 保存人下拉：`clearable filterable`，占位文案「全部用户」（与「全部产品 / 全部线名」同构） | **未选中 = 不传 `user_id` = 看全部**，不做「按角色预设默认值」（§1.3 非目标） |

### A.5 被否掉的候选（及原因）

- **只读态用琥珀警示条**（复用 FB 写表失败卡片的 3px 左脊柱）：语法对了但语气错了 —— 只读是授权结果，不是故障。降级为一枚中性 chip。
- **把「操作」列灰掉/禁用**：视觉上仍在暗示「这里本该能点」。整列撤掉更诚实（且普通 user 不受影响）。
- **给户管显示完整编辑弹窗但只放行消耗输入**：与「只改消耗」的授权面不符，也徒增一个后端必 403 的入口。
- **复用 `OwnerFilterSelect` 组件**：它内含 `applyDefaultScope`（developer/admin 默认筛自己），与本页「未选中=全部」冲突，且改它会波及账户面板两条线 —— 故在两页各写一份约 12 行的轻量下拉。

### A.6 质量底线

- 键盘可达：内联输入框 `focus/select` 由 `nextTick` 保证；`Esc` 取消、`Enter` 保存，与 `AdsAccountPanel` 一致。
- 失败有话说：保存失败弹后端 `error` 原文；非法输入（非数字/负数）就地提示且不发请求。
- 未引入任何动画；`opacity` 过渡 0.15s 与既有范式同值。

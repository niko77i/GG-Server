## 1. 视觉语言基线（沿用清单）

本项目的「纯增量」原则在前端侧的体现是：**新卡片应当看起来像是原本就长在那里**。以下是从既有三个文件里读出来的既有约定，本文全部沿用，不新造视觉语言。

| 约定 | 既有出处 | 取值 |
|---|---|---|
| 卡片容器 | `SettingsPanel.vue:66`、`TtSettingsPanel.vue:121` | `el-card shadow="never"` + `style="margin-top:20px;border-left:3px solid <强调色>"` |
| 卡片头部 | 同上 | `<template #header>` 内 `<span style="font-weight:600;">{emoji} 标题</span>`，右侧角色徽标 |
| 角色徽标 | `SettingsPanel.vue:69`（`<el-tag size="small" type="warning" style="margin-left:8px;">仅管理员</el-tag>`） | 同位置、同尺寸，仅换文案与颜色 |

| 灰底分组块 | `SettingsPanel.vue:84` | `background:#f9fafb;border-radius:8px;padding:12px;` |

| 主/次按钮 | `SettingsPanel.vue:101`、`:77` | 主操作 `type="primary"`；辅助操作默认按钮；emoji 前缀（💾 📋 🔄 ⬇️） |

### 1.1 调色与语义分工（新增，仅限本文新增元素）

| 语义 | 色值 | 用途 | 对比度（vs 白底） |
|---|---|---|---|
| 户管角色强调 | `#7c3aed` | 新卡左边框、角色徽标文字、「新归属」值 | 5.69:1 ✅ AA |
| 正文说明 | `#374151` | 字段标签 | 10.2:1 ✅ AAA |
| 一级说明 | `#6b7280` | **本次新文案的灰色正文** | 4.87:1 ✅ AA |

| 危险（不可逆） | `el-alert type="error"` + `el-tag type="danger"` | 「将清空」区块 | EP 默认 |

## 2. Task 10 —— 「📊 户管看板配置」卡片

### 2.1 在设置页中的位置与视觉层级

- **位置**：GG 在 `SettingsPanel.vue` 的「📊 充值表配置」卡片**之后**；TT 在 `TtSettingsPanel.vue` 的「📊 Google 表格配置」卡片**之后**。均在 Tab「账户设置」内。
- **互斥**：既有卡片对户管是 `v-if="false"`（GG 用 `isAdmin || isDeveloper`，TT 用 `!authStore.isHuguan`），新卡片对户管是 `v-if="authStore.isHuguan"`。**户管在任一设置页只会看到一张 sheet 配置卡**，不存在并列比较，因此不存在主次冲突。
- **视觉层级（三层）**：

| 层 | 内容 | 手法 |
|---|---|---|
| 第一层：卡身份 | 抬头「📊 户管看板配置」+ 右侧「仅户管」 | 同既有卡：`font-weight:600` + 3px 紫色左边框 + 角色徽标 |
| 第二层：两个分组 | 「表格来源」/「看板同步」 | 「看板同步」用灰底块 `#f9fafb` 包裹，形成「设置」与「动作」的物理分层 |
| 第三层：说明 | 后果说明、空态、结果提示 | 12px `#6b7280` 灰字 / `el-alert` |

**关键取舍**：「保存配置」与两个同步按钮**不在同一行**。「保存」属于第一组（它就是保存上面那两个字段），两个同步按钮属于第二组。把「安全操作」和「有后果的操作」混排在一行，是让户管误点的头号原因。

### 2.3 组件选型与关键 props

| 区域 | 组件 | 关键 props / 说明 |
|---|---|---|

| 卡片头部 | `el-tag` | `size="small"`；「仅户管」徽标，见下 |
| 表格地址输入框 | `el-input` | `v-model="hdForm.spreadsheet_id"`、`placeholder`、`style="flex:1;"`、`:disabled="hdBusy"` |
| 「读取工作表」 | `el-button` | `:loading="hdReading"`、`:disabled="hdBusy"` |
| 工作表名 | `el-select` | `v-model="hdForm.sheet_name"`、`filterable`、`allow-create`、`default-first-option`、`style="width:100%;"`（注意：**不**用 `flex:1` 的 flex 行，改为整行宽度，见 §6.2） |
| 「保存配置」 | `el-button` | `type="primary"`、`:loading="hdSaving"`、`:disabled="hdBusy"` |

| 结果提示 | `el-alert` | `:title="hdHint"`、`:type="hdHintType"`、`show-icon`、`closable`、`style="margin-top:12px;"` |
| 卡片加载态 | 卡片 body 外层 `div` | `v-loading="hdLoadingConfig"` |
| 禁用态说明 | `el-tooltip` | 包住两个同步按钮，`content="请先填写表格地址、选择工作表并保存配置"`、`:disabled="hdConfigured"` |

**派生状态**（不是新接口，纯前端计算）：

```js
const hdBusy = computed(() => hdReading.value || hdSaving.value || hdPushing.value || hdSyncing.value)
const hdConfigured = computed(() => !!(hdForm.value.spreadsheet_id && hdForm.value.sheet_name))
```

**角色徽标改用紫色文字而非 `type="warning"`**：

```vue
<span style="margin-left:8px;font-size:12px;font-weight:500;color:#7c3aed;">仅户管</span>
```

理由：(1) 既有「仅管理员」用 `el-tag type="warning"`，其文字色 `#e6a23c` 在白底上约 2.1:1，**不达 AA**，不复制这个缺陷；(2) 紫色与卡左边框同色，一次建立「紫色 = 户管专属」的关联，下次户管在别处看到紫色就知道是自己的东西。

**按钮命名对照（与计划文本的差异，需裁定，见 §9-1）**

| 方向 | 本文用 | 计划/规格原文用 |
|---|---|---|
| 系统 → 表 | `🔄 刷新到看板` | `🔄 同步到看板` |
| 表 → 系统 | `⬇️ 从表同步到系统` | `⬇️ 从看板同步` |

理由：计划的两个名字都含「同步」+「看板」，只有介词不同（`同步到看板` / `从看板同步`）。对户管这是**最容易点反的一对按钮**，而点反的后果不对称（一是冲掉手改、一是改系统数据）。本文用「**刷新**到看板」与「**从表同步回**系统」把动词错开，并让方向词紧贴动词。

### 2.5 状态设计

| 状态 | 触发 | 呈现 |
|---|---|---|
| **配置加载中** | 卡片挂载 | body `v-loading`；输入框可交互但为空 |
| **空态（未配置）** | `spreadsheet_id` 或 `sheet_name` 为空 | 两个同步按钮 `disabled` + tooltip；`hdHint` = `还没配置看板表格。填写表格地址和工作表名，点「💾 保存配置」后才能同步。`（`type="info"`） |
| **已配置** | 两个字段都有值 | 按钮启用；`hdHint` 清空 |
| **读取工作表 · 进行中** | 点击 `📋 读取工作表` | 按钮 `:loading`；其余控件 `disabled` |
| **读取工作表 · 成功（n>0）** | —— | 说明行变绿：`✅ 已加载 {n} 个工作表可供选择`；`ElMessage.success('已读取 {n} 个工作表')` |
| **读取工作表 · 成功但 n=0** | —— | `ElMessage.warning('这个表格里没有可读的工作表，请检查表格地址或表格权限。')`；下拉空态文案同上 |
| **读取工作表 · 失败** | 接口报错 | `ElMessage.error(err \|\| '读取工作表失败')`（沿用既有做法，不加行内错误块） |
| **保存 · 成功** | —— | `ElMessage.success('配置已保存')`；行内 `✅ 已保存` 2 秒后消失（沿用 `SettingsPanel.vue:462` 的做法） |
| **保存 · 失败** | —— | `ElMessage.error(err \|\| '保存配置失败')` |
| **刷新到看板 · 进行中** | 二次确认后 | 按钮 `:loading`；两个同步按钮 `disabled`（防重入） |
| **刷新成功（全部命中）** | `not_found` 为空 | `ElMessage.success('已刷新到看板：写入 {updated} 行。')`；`hdHint` = `已刷新到看板：写入 {updated} 行。`（`type="success"`） |
| **刷新成功（部分命中）** | `not_found.length > 0` | `ElMessage.warning('有 {n} 个账户不在你的表里，未写入。')`；`hdHint` = `已刷新到看板：写入 {updated} 行。有 {n} 个账户不在你的表里，没有写入。`（`type="warning"`） |
| **刷新 · 部分失败** | 500（`update_rows_by_account_id` 逐行写、失败即中断） | `hdHint` = `刷新到看板失败。Google 可能已经写入了一部分，请打开表格核对后再重试。`（`type="error"`，**不自动消失**） |
| **同步预演 · 进行中** | 点击 `⬇️ 从表同步到系统` | 按钮 `:loading`；两个同步按钮 `disabled` |
| **同步预演 · 无差异** | `summary` 三项计数全为 0 | 不开弹窗；`hdHint` = `看板与系统已经一致，没有需要同步的改动。`（`type="info"`） |
| **同步预演 · 有差异** | —— | 开差异报告对话框（Mode A，见 §4） |
| **同步预演 · 失败** | 接口报错 | `ElMessage.error(err \|\| '从看板同步失败')` |
| **同步落库 · 成功** | —— | 对话框切 Mode B（见 §4.6）；`hdHint` = `已同步：新增 {created} 个账户，更新 {updated} 处，归属变更 {owner_changed} 个。`（`type="success"`） |
| **同步落库 · 部分失败** | `not_applied.length > 0` | Mode B 内的 `not_applied` 区块（见 §4.6）；`hdHint` 用 `type="warning"` 并附同一句话 |
| **同步落库 · 失败** | 接口报错 | **不关弹窗**，在对话框顶部插入 `el-alert type="error"`：`同步失败：{err}` + `描述：系统没有写入任何数据（或只写入了一部分），请重试。`；底部按钮变 `[关闭] [重试]` |

> 「配置已保存」这 2 秒消失的行内绿字，沿用 `SettingsPanel.vue:462-463` 的既有做法（`msg` + `setTimeout`），不改成 `el-alert`，避免与 `hdHint` 撞在一起。

### 2.6 空数据 / 加载态的低成本约定

- 卡片 body 的 `v-loading` 直接用 EP 默认 spinner，不自定义文案（EP 的 `element-loading-text` 会加在遮罩中央，与既有全仓做法不一致）。
- 「读取工作表」的加载不阻塞卡片其他部分，只有按钮转圈 + 控件禁用，**不用全屏 loading**（读一张大表可能要 1~3 秒，户管还需要能改输入框内容）。

## 3. 「🔄 刷新到看板」二次确认弹窗（完整设计）

规格 §6.4 记录：全量刷新会覆盖表侧未同步的手改，**必须**在确认文案里逐列写明。这是本弹窗存在的唯一理由。

### 3.1 选型

| 项 | 取值 | 理由 |
|---|---|---|
| 组件 | `el-dialog`（不是 `ElMessageBox`） | 覆盖清单要按列分组呈现，纯文本挤在 `ElMessageBox` 里读不动；`customStyle:{whiteSpace:'pre-line'}` 换行也不够 |
| `width` | `600px` | 比 `AccountModal` 的 500px 宽一档，容得下「列 · 名称 · 说明」三列 |
| `top` | `8vh` | 弹窗不高，靠上更稳 |
| `:close-on-click-modal` | `false` | 误点空白处丢掉整份说明，代价不对称 |
| `:close-on-press-escape` | `true`（默认） | Esc = 取消，安全 |
| 焦点 | 打开后焦点落在**「取消」按钮** | 见 §6.3 键盘 |
| 底部按钮顺序 | `[取消]` 在左，`[确认刷新]` 在右 | 破坏性操作的确认键不放最左 |
| 确认按钮 type | `warning` | 这不是错误，是「有代价的常规操作」，与 `primary` 的「保存」区分开，避免肌肉记忆误点 |

### 3.3 「覆盖列清单」为什么用 `el-table` 而不是纯文本

| 方案 | 问题 |
|---|---|

| `<ul>` 列表 | 没有列头，`D 列` 与 `MCC` 的对应关系靠缩进猜 |
| **`el-table`（本文）** | 三列对齐，扫一眼就能找到「G 列 运营」，且与账户面板里的表格是同一套视觉，不需要二次学习 |

### 3.5 为什么列了两组「会覆盖的列」

规格 §6.4 点名的「户管手改列」是 `D/F/G/I/J/K`。但**系统实际写入区间是 `A:D` + `F:G` + `I:K`**，A/B/C 三列也在写入范围内。只写 `D/F/G/I/J/K` 会让户管以为改 A（日期）没事，实际会被冲掉。设计上把两组分开陈述：

- 主表 = 户管**可能主动手改**的列（改了会丢）
- 「另外」一行 = 系统本来就当权威的列（A/B/C），列出来是为了**说全**，不是为了吓人

两者的视觉权重不同（主表 vs 一行灰字），既完整又不制造噪音。

## 4. 「⬇️ 从表同步到系统」差异报告对话框（完整设计）

### 4.1 这是本设计的核心界面

规格 §12.2：「归属变更权限很大……护栏是差异确认页。**这道护栏必须真的绑得住**」。因此这个对话框不是「展示用的报告」，是**唯一的人工关卡**。设计目标按优先级：

1. **归属变更必须第一眼看到**（改错人没有第二次机会）
2. **「将清空」必须显眼且不可折叠**（不可逆）
3. 五类差异可逐条勾选，勾选结果直接等于 `confirmed` 里的账户ID
4. `not_applied` 必须在落库后显式回报（消除静默丢弃）

### 4.2 选型

| 项 | 取值 | 理由 |
|---|---|---|
| 组件 | `el-dialog` | 单个 `ElMessageBox` 装不下五类差异 + 逐条勾选 |
| `width` | `880px` | 表格有「表行 / 账户ID / 原归属 / → / 新归属 / 来源」6 列，低于 800px 会挤 |
| `top` | `5vh` | 内容长，尽量往上靠，减少内滚动 |
| `:close-on-click-modal` | `false` | 误点空白处丢掉已勾选状态，代价高 |
| 表体滚动 | dialog body `max-height:70vh; overflow-y:auto;` | 让 header 与 footer 常驻，户管随时能看到「确认同步」按钮 |
| 勾选组件 | `el-table` 的 `type="selection"` | 与 `confirmed:{create,update,owner}` 三个数组天然对应（按账户ID） |
| 分组容器 | ①②③ 常显；④⑤ 用 `el-collapse` | 见 §4.4 |
| 统计 | `el-descriptions :column="3" border size="small"` | EP 原生，六项两行排布 |

### 4.4 五个区块的信息层级（这是「一眼看出哪些会被改」的答案）

| 序 | 区块 | 默认展开 | 可勾选 | 视觉强调 | 理由 |
|---|---|---|---|---|---|
| ① | **归属变更** | ✅ 常显、置顶 | ✅ 默认**不勾** | 3px `#7c3aed` 左边框 + 区块标题 `font-weight:600` + `el-alert type="warning"` | 改错人不可撤销；「新归属」用紫色加粗，与卡的「户管色」一致 |
| ② | **将清空** | ✅ 常显 | ❌（是③的子集） | `el-alert type="error"` + 红色左边框 + 逐行列字段名 | 不可逆，规格 §8.3 明确要求「必须摆到户管眼前」 |
| ③ | 新增账户 | ✅ 常显 | ✅ 默认**勾选** | 普通区块 | 常规同步，量最大但最少意外 |
| ④ | 字段更新 | ✅ 常显 | ✅ 默认**勾选** | 普通区块 | 同上。展开行给出「字段 → 新值」明细 |

| ⑥ | 警告 | ❌ 折叠 | ❌ | `el-collapse`，标题带计数；展开后每行一个 `el-tag type="warning"` 前缀 | 户管需要去表里修，但不是在这次同步里决策 |

**为什么归属变更默认不勾选，而新增/更新默认勾选**

- 新增/更新是户管点这个按钮的**预期目的**，全部默认勾上，他扫一眼计数就能确认。
- 归属变更是**改别人的户**，规格 §12.2 说「权限很大」。把默认值设成「不勾」意味着户管必须**逐条主动点**——这才叫「逐个确认才落库」。默认全勾的话，一次点击就把护栏降级成走形式。
- 副作用是正面的：`确认同步` 按钮的「已选 N 项」会真实反映户管的选择；如果归属变更一条没勾，按钮就是普通同步。

**为什么清空区块不做成折叠**

规格 §8.3：「确认弹窗必须把『哪些列将被清空』显式摆到户管面前，不能让它藏在几百行差异里」。折叠即「藏」。封顶 20 行 + `[展开全部]` 而不是硬截断，是「不藏」的补充。

## 5. Task 11 —— 账户面板「户归属」列

### 5.1 先回答「它与既有「归属人」类字段是什么关系」

**结论：它们本来就是同一个东西（都落到 `owner_id`），只是站在两个位置、干两件事。**

| | 工具栏的「归属人」下拉 | 表格新增的「户归属」列 |
|---|---|---|
| 组件 | `OwnerFilterSelect`（`components/OwnerFilterSelect.vue`） | `el-table-column` + `el-select` |
| 位置 | 表格**上方**的筛选条 | 表格**内部**的一列 |
| 作用 | **筛选**（只读，决定看到哪些行） | **编辑**（写库，决定这户归谁） |
| 默认值 | 户管恒为「全部用户」（`ownerScope.js:11`） | 无默认，逐行显示该行当前归属 |
| 会不会改数据 | 不会 | 会 |

**用户困惑的真实风险与对策**：

风险 1 —— **两个下拉长得像**（都是 `filterable` 的用户下拉），户管可能在上面的筛选框里找归属人却找不到「改」的效果。
对策 A（本文采用）：**利用表格边界做区隔**。筛选条在表格外、列在表格内，这是既有账户面板本来就有的空间语法（`el-table` 有清晰的表头行与外框）。不新增任何控件。
对策 B（可选增强，见 §9-4）：给 `OwnerFilterSelect` 加一个**可选** `placeholder` prop，默认值保持 `全部用户` 不变；户管面板传入 `按归属人筛选`。这是纯增量的 prop 扩展，但会改到共享组件。

风险 2 —— **词汇分裂**：「归属人」/「户归属」两个词指同一个 `owner_id`，将来会有第三个说法。

**我的建议**：

1. **列名用「户归属」**，不用「归属人」。理由：用户的原始需求原话就是「ui增加一个户归属」（规格 §9.2 引文）。设计师改用户定的词，是在制造第三种说法。
2. **不在列名上做解释，用表头 tooltip 承接**。列头加 `el-tooltip`（见 5.3），内容是那句关键的业务规则：
   > `这个户归谁管。改这里会把新归属写进看板的「重新分配」列（TT 是「换绑情况」列），等你在看板同步时生效。`
   
   这一句同时解释了「户归属是什么」「改了之后去哪儿了」「什么时候生效」——三个户管必然会问的问题。
3. **不要为了消歧给工具栏下拉改名或加前缀**，除非同时做 §9-4 的可选 prop。理由：`OwnerFilterSelect` 是 GG / TT / FB 多面板共享组件（`AdsAccountPanel.vue:41`、`TtAccountPanel.vue:45` 等），直接改它的文案会波及所有平台所有角色，违反纯增量。
4. **不要把这个字段也加到 `AccountModal.vue` 的编辑弹窗里**。理由：`AccountModal` 已有「认领 / 转移给我」（`AccountModal.vue:194-199`、`:238`）这条归属通路，再加一个下拉会出现同一弹窗内两个地方都能换归属，而它们的后端语义不同（认领走 `reassign` 带字段更新，户归属走 `reassign` 只带 `owner_id`）。同一个动作两个入口、两种副作用，才是真正的困惑源。

### 5.2 列的呈现：常显下拉（静息态去边框）

三条候选路线：

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A. 沿用本表既有的「文本 + ✏️ 点击编辑」（`inline-edit-cell`） | 与账号名称 / MCC / 时区 / 代理 / 状态 五列完全同构 | 户管改归属是高频日常动作，每次 2 次点击 + 先要发现铅笔图标；且只读文本态要额外查 `ownerOptions` 才能显示人名 | ✗ |
| B. 常显 `el-select`（计划基线） | 读值与写值一处完成，可编辑性天然可见 | 每行一个带边框的方框，20 行 = 20 个边框，与「信息密度要低」冲突；视觉上比只读列重得多 | 可行，但偏重 |
| **C. 常显 `el-select` + 静息态去边框（本文主推）** | 静息时看起来就是一段人名文本（低密度）；悬浮 / 聚焦时边框浮现，可编辑性在被需要时才出现；键盘 Tab 到时焦点环会出现，正好补上「这里能改」的提示 | 需要 `:deep()` 覆盖 EP 内部类，有升级风险 | ✓ |

**方案 C 的样式（与仓库既有 `:deep()` 用法同源，见 `AdsAccountPanel.vue:495`）**：

```css
/* 静息态：看起来是文本 */
.owner-cell :deep(.el-select__wrapper) {
  box-shadow: none;
  background: transparent;
  padding-left: 0;
}
/* 悬浮或聚焦时：恢复成控件 */
.owner-cell:hover :deep(.el-select__wrapper),
.owner-cell :deep(.el-select__wrapper.is-focused) {
  box-shadow: 0 0 0 1px var(--el-border-color) inset;
  background: var(--el-fill-color-blank);
  padding-left: 11px;
}
```

`padding-left` 的变化是为了让文本在两种状态下**不左右跳动**（EP 的 wrapper 默认有内边距，去边框时要一并去掉）。

**列的位置与宽度**（两平台一致）：

| 项 | 取值 | 理由 |

### 5.4 单元格的四种形态

| 形态 | 条件 | 呈现 |
|---|---|---|
| **加载中** | `ownerOptions` 未就绪 | `el-skeleton :rows="1" animated`（约 1 屏 × 20 个骨架条，持续 <1s）。**不用裸 `el-select`**：`el-select` 在没有匹配 option 时会退化成显示 `row.owner_id` 的**裸数字**（如 `7`），户管会以为归属人叫「7」 |
| **正常** | `owner_id` 有值且能在 `ownerOptions` 里找到 | `el-select`，显示 `display_name \|\| username` |
| **未知归属** | `owner_id` 有值但不在 `ownerOptions` 里 | `el-select` **disabled**，显示 `用户 #{id}`，外层 tooltip 说明原因并要求重选。**不禁用会让户管误以为可以「保持现状」而其实提交会失败** |
| **未分配** | `owner_id` 为空 | `el-select` 显示 placeholder `未分配`（灰字），外层 tooltip 说明「普通用户看不到它」 |

> **为什么「未知归属」是个真问题**：`GET /api/platform/users`（`main.py:6256-6281`）的 SQL 是 `(u.platform = ? OR u.role = 'developer') AND u.role != 'hidden' AND (u.role = 'huguan' OR EXISTS(该平台未删账户))`。它的设计目的是**筛选**（「只列有账户的用户」，docstring 明写「选中一个名下无户的人必然得到空表，这种选项没有筛选价值」）。**而「改归属」需要的是全量用户列表**——两者诉求相反。CC 上会出现：给一个 GG 账户换到一个只在 TT 有户的人名下 → 该人不在列表里 → 单元格进「未知归属」态。
> 规格 §9.2 说「复用 `GET /platform/users`」，本文照做，但把这个缺口显式设计出来（而不是让裸数字悄悄出现）。彻底修法见 §9-4。

### 5.5 编辑交互与反馈

| 步骤 | 呈现 |
|---|---|
| 1. 选择新归属 | `@change="v => changeOwner(row, v)"` |
| 2. 乐观更新 + 锁定 | `row.owner_id = v`（立刻显新值）；`ownerPending.add(row.id)` → 该格 `el-select :disabled` |
| 3. 请求 | `accountsApi.reassign(row.id, { owner_id: v })`（TT：`ttAccountsApi.reassign`） |
| 4. 成功 | `ownerPending.delete(row.id)`；`ElMessage.success(...)`（文案见 5.6） |
| 5. 失败 | `row.owner_id = prev`（回滚）+ `ownerPending.delete(row.id)` + `ElMessage.error(err \|\| '归属变更失败，已还原')` |

**「锁定」是必要的，不是保险**：计划基线的 `changeOwner` 里 `const prev = row.owner_id` 在连续两次快速改动时会取到**上一次乐观更新的值**；若第二次失败，回滚到的是「第一次的目标值」而非真值——一次失败会留下一个假值。`:disabled="ownerPending.has(row.id)"` 在请求在途时禁掉该格，从交互层堵住这条路径。

**成功文案**

| 平台 | 文案 |
|---|---|
| GG | `归属已变更为「{新归属名}」` |
| TT | `归属已变更为「{新归属名}」` |

**关于计划基线那句「系统已把新归属写进看板的「重新分配」列」——本文建议删除，理由见 §9-2（它是条件为真的陈述：只有当这个户管配置了看板时才会写，未配置时静默跳过，`§6.3`）。** 若无法改后端返回体，退而求其次的最小实现：

| 平台 | 退让文案（后端无新增字段时的下限） |
|---|---|
| GG | `归属已变更为「{新归属名}」。如果配置了户管看板，系统会把新归属写进「重新分配」列。` |
| TT | `归属已变更为「{新归属名}」。如果配置了户管看板，系统会把新归属写进「换绑情况」列。` |

加「如果配置了」四个字，把一句假话变成一句真话，成本为零。

### 5.6 「户归属」列的空态 / 加载态 / 失败态（汇总）

| 状态 | 呈现 |
|---|---|
| 面板首次加载（用户列表未回） | 该列每格 `el-skeleton`；不影响表格其余列的使用 |
| 用户列表加载失败 | 该列 `el-select` 一律 `disabled` + placeholder `暂时无法加载用户列表`；表格顶部一次性 `ElMessage.warning('用户列表加载失败，暂时无法修改户归属。')`；**不阻塞**账户表格（沿用 `OwnerFilterSelect.vue:56` 的「静默失败不阻塞主流程」口径，但此处要出声，因为这一列是写操作） |

| 提交失败 | 值回滚 + `ElMessage.error` |

## 8. 关键取舍（决策记录）

### 8.1 「户归属」字段与既有字段的关系

| 取舍 | 结论 | 理由 |
|---|---|---|
| 列名叫什么 | 「户归属」（用户原话） | 不改用户定的词，避免第三套说法 |
| 和工具栏「归属人」筛选冲突吗 | 不冲突，靠**位置的语义**区隔（筛选在表外，编辑在表内） | 不动共享组件，纯增量 |
| 要不要也加到 `AccountModal` 弹窗 | **不加** | `AccountModal` 已有「认领 / 转移给我」这条路；同一弹窗两个归属入口、两种后端语义 = 真困惑源 |
| 要不要再加「归属人」只读列 | **不加** | 户归属列已经承载了「当前值」的只读展示（静息态就是文本） |
| 呈现方式 | 常显下拉 + **静息态去边框**（方案 C） | 读值与写值一处完成、低密度、可编辑性按需浮现。见 §5.2 |
| 非户管 | `v-if` **不渲染**（不是禁用） | 规格 §9.2 明确要求 |
| 未知归属人 | 显示 `用户 #{id}` + disabled + tooltip | 不让裸数字出现，也不让户管以为能保持现状 |

### 8.2 差异报告：表格还是分组列表

| 取舍 | 结论 | 理由 |
|---|---|---|
| 整体结构 | **分组区块 + 区块内用 `el-table`** | 分组负责「哪儿会被改」的一眼判断，表格负责「改成什么」的精确读取；两者不能互相替代 |
| 排序 | 按后果严重度，不按后端键顺序 | 注意力预算只有前两屏 |
| 归属变更的强调色 | **紫（户管色），不是红** | 它是这个功能的主用途，不是异常；染红会让户管以为自己做错了 |
| 归属变更默认勾选状态 | **不勾** | 规格 §12.2 要求「逐个确认才落库」；默认全勾会把护栏降级成形式 |
| 清空区块 | 常显 + `el-alert type="error"` + 逐行列字段名 + `[展开全部]`（不硬截断） | 规格 §8.3「不能藏」 |
| 跳过 / 警告 | `el-collapse` 折叠，标题带计数 | 不需要在本次决策，但必须可见 |
| 字段名 | 前端 label 映射表（§4.9） | 后端给的是 `acquired_date` 这类数据库字段名，户管读不懂 |
| `_is_dead` | 映射为 `是否封户` / `是否回收` 并显示 | 它是 `fields` 里真实存在的键，不映射就会露出 `_is_dead` |
| 警告文案里的 `agent_name` 等 | 前端 token 替换 | 后端文案夹带英文字段名 |

### 8.3 部分失败怎么表达

| 层 | 场景 | 表达 |
|---|---|---|
| **① 落库部分失败（`not_applied`）** | 户管勾了、但落库时表已变、当前 diff 找不到该账户 | 对话框切 Mode B，**停在那里不自动关**，`el-alert type="warning"` 明确说「有 N 项没有落库（确认之后表又变了）」，逐条列账户ID + 中文类别，并给出下一步动作「请重新点「⬇️ 从表同步到系统」再看一次」。**不做 toast**——toast 会消失、超 20 条会被截断，而规格 §8.3 要求「不能静默丢弃」 |
| **② 刷新到看板的中途中断** | `update_rows_by_account_id` 逐行写、失败即抛 | 卡片上的 `hdHint` 常驻 `type="error"` 提示：`刷新到看板失败。Google 可能已经写入了一部分，请打开表格核对后再重试。` **不自动消失**（户管需要它留着） |
| **③ 刷新到看板的「部分命中」** | 表里没有某些账户（`not_found`） | `ElMessage.warning('有 {n} 个账户不在你的表里，未写入。')` + `hdHint type="warning"` 常驻。这是**正常结果**不是失败，所以用 warning 不用 error |
| **④ 单行名称歧义** | MCC / 渠道 / BC 名匹配不到或重名 | 进 `warnings`，第 ⑤ 折叠区；同时该列不落库、该行其余列照常（后端已实现）。前端不额外做提示——它已经在报告里 |

**贯穿原则**：**「计数正确就报成功」是不允许的**。任何一个「勾了但没落」的项，都必须在界面上有它自己的位置，而不是被折进一个数字。

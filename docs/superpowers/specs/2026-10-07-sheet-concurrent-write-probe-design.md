# 写表并发探测（一期：只观测，不防护）

> **日期**: 2026-10-07
> **状态**: 方案已与用户确认，待实现
> **一期范围**: 只做**观测** —— 探测同一张 Sheet 的并发在途写，命中写日志
> **明确不做**: 加锁 / 串行化 / 自动重试 / 对账。这些都是**二期**的事，且要等本期数据出来再决定

---

## 1. 需求描述

用户原话：

> 「表和库到底一不一致 这个之前没这么多人使用，是一致的。我只是担心后续出问题」

即：**历史没有问题**（数据支持见 §2），用户担心的是**当前 6 人规模扩到约 80 人之后**会不会出问题。

用户已确认的实际诉求是「提前防护」，而不是「排查历史」。因此本设计**不做历史对账**。

## 2. 现状诊断（2026-10-07 实测数据）

| 观测项 | 实测值 | 来源 |
|---|---|---|
| 写表总次数 | 903 次 / 69 天 | `sheets_sync_log` |
| 日均 | 13 次（峰值 29） | 同上 |
| 失败率 | 1.4%（13/903） | 同上 |
| **429 / 配额错误** | **0 次** | 同上，关键词全文匹配 |
| 历史失败成因 | 403 权限 ×4、产品不存在 ×4、503/502 ×3、配置 ×2 | 同上 |
| 实际写表用户 | **仅 6 人**（95% 集中在 2 人） | 同上 按 user_id 分组 |
| 跨用户并发写同表 | **0 次**（同 line_name + 60s 内 + 不同 user） | 同上 JOIN 查询 |

**结论**：

- **配额不是风险** —— 实测 13 次/**天**，配额是 60 次/**分钟**，差三个数量级
- **并发丢更新当前未发生，但样本只有 6 人，不能外推到 80 人** —— 这正是本期要观测的对象

### 2.1 为什么单把「并发」拎出来观测

三个候选风险里，只有并发是**质变**而非量变：

| 风险 | 人数从 6 → 80 时的变化 |
|---|---|
| 写失败 | 线性增长，且会**报错、进日志**，可发现 |
| 配额 | 仍差两个数量级，**安全** |
| **并发丢更新** | **概率随人数上升，且完全静默** —— 两边都返回成功，只有事后发现少行 |

失效机理（`google_sheets_service.py` 的写函数普遍是 read-modify-write）：

```
线程1: get 整张表 → 定位 → 准备写回（含 A 行）
线程2: get 整张表 → 定位 → 准备写回（含 B 行，不含 A）
线程1: 写回
线程2: 写回              ← A 行被覆盖，且无人报错
```

`sheet_write.py:23` 已有的 `_inflight` 集合只能防**同一 (user_id, target, business_key)**，
防不住「**不同账户写同一张 Sheet**」。

## 3. 目标行为 / 非目标

**目标**：回答一个问题 —— 「80 人规模下，同一张 Sheet 会不会出现并发在途写？多频繁？」

**非目标**（一期明确不做）：

- ❌ 不做串行化 / 加锁（会改变写表行为与延迟，现在没有证据支持）
- ❌ 不做自动重试或冲突消解
- ❌ 不做历史对账
- ❌ 不改任何写表函数的**逻辑**

## 4. 技术方案

### 4.1 探测点：装饰器，而非改函数体

在 `google_sheets_service.py` 新增一个装饰器 `probe_concurrent_write`，给写函数**各加一行**。

**为什么用装饰器**：`google_sheets_service.py` 里的写函数体普遍 40~80 行，若在函数体内插桩需整体缩进，
违反「纯增量」原则且易引入缩进事故。装饰器只加一行、不动函数体。

**为什么用 `inspect.signature` 提取参数**：写函数签名不统一（详见 §4.5），
硬编码位置会在后续签名调整时静默失效。

### 4.2 数据结构

```python
# (spreadsheet_id, sheet_name) -> {线程 ident: 重入深度}
_active_writes = {}
_active_writes_lock = threading.Lock()
```

**为什么存 `{线程: 深度}` 而不是「纯线程集合」或整数计数器**：

- 整数计数器的语义是「进入次数」，同一线程嵌套会误报成并发
- 纯线程集合虽能给出「几个不同线程」，但**去重会丢掉重入信息**：同一线程嵌套时
  内层返回就判定「集合空 → 删 key」，而此时外层**仍在写表** —— 注册表谎报
  「没人写」，外层在途期间的所有并发全部漏报（code review I1，已运行时复现）
- `{线程: 深度}` 同时给出两个语义：`len(dict)` 是「几个不同线程」（要测的量），
  深度则保证只有**最外层**退出才真正摘除 key

### 4.3 键的选择：`(spreadsheet_id, sheet_name)`

冲突只发生在**同一张表**上 —— 两个运营写不同产品的不同表格不会互相覆盖。

`sheet_name` 可为 `None`（部分写函数签名里没有，如 `upsert_zuobiao` / `_upsert_rows`）。
**`None` 必须按「通配」参与匹配** —— 与同 `spreadsheet_id` 下的任何 sheet 都视为可能冲突：

- 若让 `None` 作为普通值比较，`(sid, None)` 与 `(sid, "看板")` **永不相等**，跨路径
  写同一张表的并发会**漏报**，而漏掉的恰好是 `upsert_zuobiao` / `_upsert_rows`
  这两个 read-modify-write 函数（code review I2；本文档早先写的
  「不会漏报，只会多报」**是错的**）
- 通配的代价只是多报 —— 同 spreadsheet 下不同 sheet 的并发被算作冲突，而日志里
  带了 `sheet_name`，可人工分辨

**解析不出 `spreadsheet_id` 时直接跳过探测**（不注册）。否则键退化成 `(None, None)`，
所有这类调用挤在同一键上互相误报（code review I3）。探测宁可完全不生效，
也不要刷出满屏假告警。

### 4.4 开销

写表本身是网络往返（数百毫秒），锁内只做一次字典查改与集合增删（微秒级），可忽略。

`inspect.signature` 在装饰时绑定一次并缓存在闭包里，不在每次调用时重算。

### 4.5 要装饰的函数（7 个）

| 函数 | 行 | 有 `sheet_name` |
|---|---|---|
| `upsert_zuobiao` | 124 | ✗ |
| `append_recharge` | 286 | ✓ |
| `append_recharge_tt` | 369 | ✓ |
| `append_recycle` | 450 | ✓ |
| `update_cell_by_account_id` | 590 | ✓ |
| `update_rows_by_account_id` | 652 | ✓ |
| `_upsert_rows` | 808 | ✗ |

**不装饰 `upsert_fb_reports`（733）**：它的签名里**没有** `spreadsheet_id`
（只有 `db, user_id, product_name, line_name, ...`），一旦装饰，key 会退化成
`(None, None)`，与所有其它此类调用挤在同一键上造成跨表误报。

（早先记为「装饰两者会重复计数」**是错的** —— 真正理由是缺形参。结论不变：

## 5. 日志格式

命中时记 `WARNING`（走既有 `gg-server` logger，自动落 `temp/logs/gg-server.log`）：

**N 路并发通常产生 N-1 条日志** —— 每个「进入时已有他人在途」的线程各记一条，
告警在锁外发出。按日志行数统计「并发发生次数」时要注意这个口径，别把一次碰撞
算成多次（code review M4）。

```
[WARNING] Sheet 并发写探测：同一表 2 个线程在途 — spreadsheet_id=1pUV9... sheet='回收户清单' 入口=update_rows_by_account_id
```

字段：在途线程数、spreadsheet_id、sheet_name、被装饰函数的 `__name__`（定位入口）。

## 7. 测试策略

| 用例 | 断言 |
|---|---|
| 单线程顺序写同一表 | 不产生 WARNING |
| 两个线程并发写同一表 | 产生 WARNING，含正确线程数 |
| 同一 spreadsheet、**不同 sheet** | 不产生 WARNING |
| **不同 spreadsheet** | 不产生 WARNING |
| 同一线程嵌套进入同一 key | 不误报，**且内层返回后外层仍可见**（I1 守卫） |
| **无 `sheet_name` 的入口 × 具名入口、同 spreadsheet** | **必须告警**（I2 守卫） |
| **无 `spreadsheet_id` 的入口** | 不参与探测、不产生假告警（I3 守卫） |
| 被装饰函数抛异常 | registry 正确清理（不泄漏，后续调用不被误判为并发） |
| 装饰后函数返回值/异常 | 与原函数**逐字节一致**（透传校验） |

前两条是透明性门禁；随后三条锁的是**漏报**方向 —— 只断言「不误报」的测试
测不出漏报，而漏报会让二期的锁决策建立在失真数据上。

## 8. 风险与代价

| 项 | 评估 |
|---|---|
| 误报 | 同一线程内的**串行**两次写会被正确区分（按线程记重入深度），不会误报 |
| 多进程失效 | registry 是进程内的。当前是单进程 waitress，成立；若将来多 worker，需改为跨进程方案 —— 届时日志的「探测覆盖率」说明要一并更新 |
| 日志量 | 仅在真并发时产生，预期极低（当前 0 次） |

## 9. 后续（二期，不在本期）

本期日志跑一段时间后，用真实数据决定：

- 若**确实**出现并发 → 按 `(spreadsheet_id, sheet_name)` 加进程内串行锁（写表变临界区）
- 若**从未**出现 → 不加锁，省下串行化代价

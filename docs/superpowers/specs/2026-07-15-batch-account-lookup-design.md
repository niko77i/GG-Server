# 批量查户功能 — 设计文档

## 需求描述

在账户管理页面增加"批量查户"功能：用户可以粘贴一批账户 ID，快速查看这些账户在系统中的详细信息（归属、状态、代理、MCC 等），不需要走批量导入流程。

## 与现有功能的区别

| 功能 | 批量导入 | **批量查户（新）** |
|---|---|---|
| 入口 | AdsAccountPanel → "📥 批量导入" 按钮 | AdsAccountPanel → "🔍 批量查户" 按钮（新增） |
| 用途 | 导入/认领新账户 | 纯查询，快速了解一批账户的状态 |
| 流程 | 解析ID → 查库 → 区分新旧 → 编辑 → 提交创建/认领 | 输入ID → 查库 → 展示结果 → 完成 |
| 后端 | batch-lookup（已有） | **复用** batch-lookup 接口 |

## 技术方案

### 后端：复用已有接口

已有 `POST /api/accounts/batch-lookup`（[main.py:2840](py/main.py#L2840)）功能完全满足查户需求：

- 输入：`{ account_ids: ["123-456-7890", ...] }`
- 输出：`{ found: [...], not_found: [...] }`
- found 中每个账户包含：id, name, account_id, timezone, agent, status, acquired_date, mcc_id, mcc_name, mcc_code, owner_id, owner_name

**不需要改后端**。

### 前端：新增批量查户弹窗

#### 1. 新建组件 `AccountBatchLookupModal.vue`

核心功能：
- Textarea 输入区：粘贴账户 ID（每行一个，自动解析提取）
- 解析统计：识别数量、格式不符数量
- 查询按钮：调用 `accountsApi.batchLookup()`
- 结果表格：展示 find 的账户详情 + not_found 列表

结果展示字段：

| 列 | 说明 |
|---|---|
| 账户 ID | account_id |
| 名称 | name |
| 所属 MCC | mcc_name (mcc_code) |
| 时区 | timezone |
| 代理 | agent |
| 状态 | status（彩色标签） |
| 到手时间 | acquired_date |
| 归属人 | owner_name |

#### 2. 修改 AdsAccountPanel.vue

在工具栏加一个"🔍 批量查户"按钮，点击打开 `AccountBatchLookupModal`。

## 实际代码逻辑补充（2026-07-23 审计）

以下内容在设计文档中未提及或描述不够精确，根据实际代码补充。

### 1. ID 提取规则（`extractAccountId`）

`AccountBatchLookupModal.vue` 中的 ID 提取逻辑与批量导入共用，支持四种输入格式：

| 优先级 | 输入示例 | 提取方式 |
|---|---|---|
| 1 | `123-456-7890` | 精确匹配 `^\d{3}-\d{3}-\d{4}$` 格式 |
| 2 | `账号 123-456-7890 备注` | 正则提取第一个 `\d{3}-\d{3}-\d{4}` 子串 |
| 3 | `1234567890` | 10 位纯数字自动格式化为 `123-456-7890` |
| 4 | `ID:1234567890 extra` | 正则提取第一个 10 位连续数字，再格式化 |

只有上述四种方式都无法提取时，该行才计入"格式不符"。

### 2. 自动去重

`parsedIds` computed 中使用 `Set` 自动去重。即使用户粘贴了重复的 ID，查询时只发一次、识别计数也只算一次。原始设计文档中未提及去重行为。

### 3. 格式不符统计

`invalidIds` computed 统计有文本内容但无法提取出有效 ID 的行数。这独立于 `parsedIds` 计数，两者之和可能超过总行数（因为有些行可能既不是空白也提取不出 ID）。

解析统计显示格式：`共识别 N 个  ✕ M 个格式不符`。

### 4. 弹窗生命周期：打开即重置

弹窗使用 `@open="init"`，每次打开时自动调用 `init()` 清空 `idText`（输入框）和 `result`（查询结果）。这样用户每次打开都是一个干净的查户界面，不会残留上次的结果。设计文档未提及此行为。

### 5. 查询按钮动态文案

按钮文字不是固定的 `🔍 查询`，而是动态显示当前识别到的 ID 数量：
```
🔍 查询（5 个）
```
未识别到 ID 时按钮 `disabled`，不显示数量后缀。

### 6. 状态标签颜色映射

设计文档只说"彩色标签"。实际代码中有精确的颜色映射规则：

| 状态值 | Element Plus `type` | 颜色语义 |
|---|---|---|
| `死亡` | `danger` | 红色 |
| `存活` | `success` | 绿色 |
| `验证` | `warning` | 橙色 |
| 其他（含空值） | `info` | 灰色，显示文字 "未知" |

### 7. 空值处理的 UI 细节

设计文档未描述以下边界情况的具体呈现：

- **MCC 未分配**（`mcc_name` 为空）：显示灰色文字 `未分配`，不显示 `mcc_code`
- **归属人为空**（`owner_name` 为空）：显示灰色短横 `—`
- **状态为空**：`el-tag` 显示 `未知`（灰色 `info` 类型）
- **归属人非空**：使用 `el-tag type="warning"`（橙色标签）包裹显示 `owner_name`

### 8. 未找到列表的样式

设计文档仅示意了未找到的 ID 列表，未描述样式。实际实现：

- 红色背景区域：`background:#fef2f2; border:1px solid #fecaca; border-radius:6px`
- 文字颜色：`#991b1b`
- 最大高度 120px，超出滚动
- 每个 ID 前有 `·` 前缀

### 9. 批量查户按钮无权限/状态限制

与其他批量操作按钮（"批量充值"、"批量修改状态"、"批量修改 MCC"、"批量删除"）不同，"批量查户"按钮**没有任何禁用条件**，不需要先选中账户即可使用。这是设计层面有意的决定——查户是独立操作，不依赖当前列表选中状态。

### 10. 后端参数校验和清洗

`POST /api/accounts/batch-lookup` 实际做的前置处理比设计文档描述的更详细：

1. **类型校验**：要求 `account_ids` 必须是 list 类型，否则返回 400 错误 `"请提供 account_ids 列表"`
2. **清洗空白**：每个 ID 做 `str().strip()` 处理，过滤掉清洗后为空字符串的条目
3. **空列表短路**：清洗后列表为空时，直接返回 `{ found: [], not_found: [] }`，不查数据库
4. **去重未在后端做**：如果前端传入重复 ID，后端不做额外去重——去重责任在前端（`parsedIds` 的 `Set`）

### 11. 后端返回的完整字段列表

设计文档列举了 found 中每个账户的字段，但遗漏了 `id`（数据库主键，用于后续可能的编辑等操作）。`_account_row_to_dict` 实际返回的字段为：

| 字段 | 来源 | 说明 |
|---|---|---|
| `id` | `accounts.id` | 数据库主键（设计文档遗漏） |
| `name` | `accounts.name` | 账户名称 |
| `account_id` | `accounts.account_id` | 广告账户 ID |
| `timezone` | `accounts.timezone` | 时区 |
| `agent` | `accounts.agent` | 代理 |
| `status` | `accounts.status` | 状态 |
| `acquired_date` | `accounts.acquired_date` | 到手时间 |
| `mcc_id` | `accounts.mcc_id` | 所属 MCC 的数据库 ID |
| `mcc_name` | `mcc.name` | MCC 名称（JOIN 得来） |
| `mcc_code` | `mcc.mcc_id` | MCC 编码（JOIN 得来） |
| `owner_id` | `accounts.owner_id` | 归属人数据库 ID |
| `owner_name` | `users.display_name` / `users.username` | 归属人显示名（含兜底） |

### 12. 与 store 的关系

批量查户功能**完全不依赖 Pinia store**（`useAccountStore`）。组件直接调用 `accountsApi.batchLookup()`，查询结果完全在组件本地 state 中管理。设计文档未明确说明这一点，但这个架构决策值得记录——查户不会污染全局账户列表状态。
